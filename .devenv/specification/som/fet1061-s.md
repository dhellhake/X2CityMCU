# FET1061-S System-on-Module hardware reference

[Specification index](../README.md) · [Application specification](../application/README.md)

> Reusable module-level reference consolidated from historical Forlinx material and checked against current Forlinx and NXP documentation. Last technical audit: 2026-08-19.

## Scope, source hierarchy, and revision context

This document describes the **FET1061-S SoM**, not the X2CityMCU carrier or its external system. Historical OK1061-S carrier schematics were used only to cross-check SoM pad numbering and default net names. Project choices are recorded separately in the [application specification](../application/README.md).

The sources do not all describe the same point in the product's life:

1. The historical hardware manual is **Rev. 1.0, January 2019**. Its update table identifies manual V1.0, SoM V1.0, and carrier V1.1.
2. The historical pin-mux workbook `FET1061-S Pinmux-20190412.xlsx` contains the complete 196-ball MCU mux matrix. It marks 82 MCU connections as brought onto or used by the module, but it does not itself assign the 100 SoM pad numbers.
3. The historical CAD pack dated 2022-05-30 includes carrier revisions V1.1/V1.1A/V2.0/V2.0A plus a `FET10xx-S_V1.0.DXF` mechanical drawing. It does **not** contain the SoM schematic, PCB source, or BOM.
4. The photograph in the historical manual and on the current official product page shows a **FETRT10XX-S V1.0** PCB dated 2018-12-28 with an `MIMXRT1061CVL5A` MCU. A later public RT-Thread BSP names `MIMXRT1061CVL5B`. Inspect the marking on the actual module before applying silicon-revision errata.
5. Forlinx's current product page offers 4 MiB and optional 16 MiB QSPI NOR configurations. The photographed reference unit has a 4 MiB Winbond `W25Q32JV`-family device, top-marked `25Q32JVSIQ`.

For a pad-level design, use this document for FET1061-S wiring/board facts and the current NXP data sheet, reference manual, IOMUX definitions, and silicon errata for the exact MCU suffix. Source authority is claim-specific: NXP controls silicon behavior, electrical limits, mux modes, and errata; Forlinx documentation and physical inspection control module wiring, fitted parts, mechanics, and module limits. The reconciled findings from those historical artifacts are retained here as provenance and cross-checks, while software and marketing claims require verification. Marketing interface counts are theoretical maxima, are heavily multiplexed, and are not all simultaneously available.

This is the main FET1061-S module reference beside the official NXP chip documentation. It is still a derived document: this repository contains no SoM schematic, PCB source, production BOM, verified production land pattern, module-current maximum, or complete power-tree specification.

## Module at a glance

| Item | FET1061-S specification |
|---|---|
| Processor | NXP i.MX RT1061, `MIMXRT1061CVL5A` on the documented/photo unit; `...CVL5B` also appears in later public BSP material |
| CPU | Arm Cortex-M7 with MPU/FPU, 528 MHz supported module rating |
| On-chip memory | 1 MiB SRAM; up to 512 KiB is configurable as TCM or general OCRAM; 128 KiB boot ROM |
| Program storage | External QSPI NOR: 4 MiB Winbond `W25Q32JV` family, top mark `25Q32JVSIQ`, on the reference unit; 16 MiB is a current ordering option |
| Main input | `5V_SYS`, nominal 5.0 V, allowed 4.5–5.5 V |
| RTC/SNVS backup input | `VDD_COIN_3V3`, 3.3 V |
| Exported supply rails | No general-purpose 3.3 V output is exposed; `VDD_COIN_3V3` is an input, not an output |
| Digital I/O level | Nominal 3.3 V in the Forlinx pin table; verify the actual `NVCC_EMC`, `NVCC_SD0`, and `NVCC_SD1` bank rails on the fitted revision; never treat GPIO as 5 V tolerant |
| Form factor | 30 × 30 mm PCB; approximately 3 mm overall height |
| PCB | 1.0 mm, four layers, ENIG finish |
| Connection | 100 castellated/edge-solder pads, 25 per side, 1.0 mm pitch |
| Module temperature | −40 to +85 °C operating; −40 to +125 °C storage |
| Humidity | 10–90% RH operating; 5–95% RH storage; non-condensing |
| Software advertised/supplied by Forlinx | Bare metal/NXP SDK, FreeRTOS, RT-Thread, plus historical IAP/bootloader material; those vendor packages are not stored in this repository |

Do not confuse the 128 KiB boot ROM with rewritable program flash. Application code normally executes from the external QSPI NOR (XIP) or is copied into SRAM.

Critical integration facts:

- Feed the module through both 5 V input pads and all ground pads; do not attempt to power it through a signal, USB VBUS, RTC backup, or flash rail.
- The module exposes 3.3 V logic but does **not** export its internal main 3.3 V rail. A custom carrier must generate its own peripheral 3.3 V and prevent powered peripherals from back-powering an unpowered SoM through I/O.
- Use SoM pad 21 `POR_B` for a debugger's active-low reset connection. Pad 20 `POR_BUTTON` enters the module power/reset circuit and is not the direct MCU reset pin.
- SWD uses pad 32 `SWCLK`, pad 33 `SWDIO`, pad 21 `POR_B`, and ground. A debugger VTref must be supplied separately; see [SWD/JTAG wiring, debugger reset, and VTref](#swdjtag-wiring-debugger-reset-and-vtref).
- Forlinx explicitly reserves pad 18 / MCU ball D14 as the core-board watchdog-reset signal and warns carrier designers not to repurpose it, even though the MCU mux table lists alternatives.
- The fitted `CVL5x` MCU and complete module are specified for 528 MHz. A programmable 600 MHz clock is not a supported module operating mode. The project's intentional deviation is documented under [application clocking](../application/clocking.md).

### Integrated functions whose exact part numbers are not published

The hardware manual says the SoM integrates its power circuit, reset-monitoring circuit, and storage circuit. It also specifies a 32.768 kHz RTC clock, and a small low-frequency crystal is visible beside the 24 MHz crystal. The historical source package contained no SoM schematic/BOM, so the exact regulator, RTC-crystal MPN, and every small support IC cannot be stated reliably.

Another photographed IC has the top mark `AEBJ`, which is consistent with a Maxim `MAX6340UK29` 2.9 V open-drain reset supervisor with capacitor-adjustable delay. This is only an **unverified top-mark candidate**: no available SoM schematic, BOM, or bundled data sheet links it to that function, so do not rely on it in the reset topology. The exact DC/DC/LDO devices also remain unidentified; two `1R0` inductors and several power ICs are visible.

### What is not on the SoM

- No external SDRAM is documented or enabled in the board-specific material; the usable RAM is the MCU's 1 MiB on-chip SRAM.
- No eMMC is documented as fitted.
- The two Ethernet interfaces are MACs only. PHYs, magnetics, and connectors belong on the carrier.
- CAN/CAN-FD transceivers belong on the carrier.
- USB 2.0 high-speed PHYs are integrated in the MCU, but VBUS switching/protection and connectors belong on the carrier.
- The 2019 hardware manual's claim that both QSPI NAND and QSPI NOR are mounted conflicts with the photographed board, software configuration, bare-metal manual, and current product page, all of which establish QSPI NOR only. No fitted NAND part is verified.

### CAD-visible assembly evidence, not a BOM

The generic `FET10xx-S V1.0` DXF shows the following footprints/reference designators: `U2` SOIC-8, `U3` BGA196, `U5` SOT23-3, `U6` TSOT23-8, `U7` SOT143-4, `U10`/`U11` SOT23-5, `X1` 3225, `X2` 3215, `L1`/`L2` SWPA4020, `LED1`/`LED2` 0402, test point `T1`, and `D1`–`D5` SOD523. The photo/part evidence makes `U3` the MCU and `U2` the SOIC-8 NOR; assigning the other reference designators to inferred ICs would be speculation. Use this list for physical inspection/service orientation only, not as a production BOM or proof that every footprint is populated on every revision.

## Mechanical layout and pad numbering

Viewed from the **component side**, with the pin-1 marker at the lower-left corner, numbering proceeds around the perimeter as follows:

```text
                         75  ...  51
                     +---------------+
                  76 |               | 50
                     |   components  |
                     |               |
                 100 | •             | 26
                     +---------------+
                          1  ...  25
```

- Bottom edge: 1 → 25 from left to right.
- Right edge: 26 → 50 from bottom to top.
- Top edge: 51 → 75 from right to left.
- Left edge: 76 → 100 from top to bottom.
- Pitch is 1.0 mm; there are 25 pads per side.
- The generic V1.0 DXF places pad centers 3–27 mm along each 30 mm edge: pin 1 `(3,0)`, pin 25 `(27,0)`, pin 26 `(30,3)`, pin 50 `(30,27)`, pin 51 `(27,30)`, pin 75 `(3,30)`, pin 76 `(0,27)`, and pin 100 `(0,3)` mm in component-side coordinates with origin at the lower-left outline. It draws copper 0.50 mm tangential × 1.50 mm radial and a 0.60 × 1.60 mm solder-mask opening, centered on the outline.
- The official launch material describes single-sided component placement and the underside is component-free in the product photos, allowing direct SMT placement. Confirm courtyard, paste, and reflow requirements with Forlinx before production.
- The historical `FET10xx-S_V1.0.DXF` and `FET1060-S SoM 3D.STEP` files were only **provisional mechanical references** and are not stored in this repository. The STEP filename says FET1060-S while its internal strings refer to a 1050-S board; neither file proves an exact FET1061-S production model. Do not release a land pattern from the provisional dimensions alone; verify outline, copper/mask geometry, paste apertures, clearances, and reflow profile with Forlinx and a physical module.

### Power-rail architecture and carrier 3.3 V

- `5V_SYS` is the only general module-power input. The SoM generates the MCU and storage rails internally; the exact converter/LDO implementation and available current margin are not documented.
- No general-purpose 3.3 V output appears among the 100 pads. The 3.3 V shown for digital signals is their logic/I/O domain, not a carrier-power pin.
- Pin 27 `VDD_COIN_3V3` feeds the MCU SNVS/RTC backup domain. It is an **input** and must never be used to power carrier logic or debugger VTref.
- Pins 83 and 86 are USB VBUS input/sense nodes. They are not auxiliary 5 V outputs.
- The MCU's `VDDA_ADC_3P3`/ADC-reference rails are also internal and not exported. There is no connector pad for overriding `VREFH` or obtaining an official ADC-reference output. Ratiometric external sensing must measure the sensor excitation on another ADC channel; pin 27 is not an ADC reference.
- A custom carrier needing 3.3 V peripherals must generate its own 3.3 V from the system supply. Sequence or isolate that rail so an external device cannot drive a module I/O while the module I/O domain is off. `PMIC_ON_REQ` can control a carrier load switch or regulator enable, but it is a logic signal rather than a supply.
- The photographed W25Q32 NOR runs from the module's internal approximately 3.3 V rail. That rail is not specified as an exported supply and its spare current capacity is unknown.

### Supported CPU clock and core voltage

The documented/photo MCU is `MIMXRT1061CVL5A`; the public later BSP names `...CVL5B`. Both are speed-grade-5 industrial parts. NXP qualifies them for a maximum 528 MHz core/AHB clock (`F_SYS`) and 132 MHz IPG clock (`F_BUS`) over the industrial junction-temperature range. The complete FET1061-S module is likewise advertised at 528 MHz.

| Operating point | Ordering code / status | Core/AHB and IPG | `VDD_SOC_IN` condition |
|---|---|---|---|
| Supported module point | `MIMXRT1061CVL5A/B` | 528 / 132 MHz max | 1.15–1.26 V operating range in the current industrial data sheet |
| Supported NXP 600 MHz point | `MIMXRT1061DVL6A/B` consumer speed grade | 600 / 150 MHz | Overdrive range 1.25–1.30 V; NXP's application note uses 1.275 V nominal |
| FET1061-S at 600 MHz | Unsupported experiment | Programmable, but not qualified | No voltage makes this a specified `CVL5x` operating point |

The MCU's integrated DCDC controls the core rail in software through `DCDC_REG3.TRG` in 25 mV target steps:

```text
VDD_SOC target = 0.800 V + TRG × 0.025 V

TRG 0x0E = 1.150 V
TRG 0x12 = 1.250 V
TRG 0x13 = 1.275 V
```

The core rail is not exposed on the module connector. Do not alter `5V_SYS` or inject an external voltage to change it. When changing a supported operating point, raise voltage and wait for `DCDC_REG0.STS_DC_OK` before increasing frequency; reduce frequency before lowering voltage. Prefer the current NXP DCDC/clock driver over copied raw register code.

The clock tree can request 600 MHz, but register capability is not a speed-grade guarantee. The numerical 1.25–1.26 V overlap between the `CVL5x` 528 MHz rail range and the `DVL6x` overdrive range does not create a valid 600 MHz operating point; voltage/frequency conditions belong to their respective ordering codes. Use 528 MHz or less for a supported `CVL5x` design.

The current X2CityMCU firmware intentionally deviates from this supported point. Its exact clock tree, voltage target, transition ordering, and qualification boundary are documented in [Application: Clocking](../application/clocking.md).

See the [current industrial data sheet](https://www.nxp.com/docs/en/nxp/data-sheets/IMXRT1060IEC.pdf), [600 MHz consumer data sheet](https://www.nxp.com/docs/en/nxp/data-sheets/IMXRT1060CEC.pdf), and [NXP run/overdrive application note](https://www.nxp.com/docs/en/application-note/AN12245.pdf).

## Processor resources and important RT1061 limits

The exact RT1061 variant provides the following silicon resources. This is useful when reading the alternate-function matrix, but it does not mean every instance has a complete set of pads on the SoM connector.

- Cortex-M7 at 528 MHz, MPU/FPU, eDMA, 1 MiB SRAM, and 128 KiB boot ROM.
- SEMC external-memory controller; two GPTs; PIT; four QTimers; four FlexPWM blocks; four quadrature encoder blocks; four watchdog blocks.
- SPDIF, three SAI blocks, and MQS.
- Two USB OTG controllers with integrated high-speed PHYs.
- Two USDHC SD/eMMC controllers.
- Two 10/100 Ethernet MACs with IEEE 1588 support.
- Eight LPUART, four LPI2C, four LPSPI, two FlexSPI, two classical FlexCAN plus one FlexCAN with CAN-FD, and three FlexIO blocks.
- 127 GPIOs (124 tightly coupled at the MCU level), two ADCs, four analog comparators, and a touch-screen controller.
- HAB secure boot, DCP, BEE, TRNG, SNVS, and SJC security/debug facilities.
- Integrated DCDC, temperature sensor, and power-management control.

**RT1061 has no LCDIF, CSI camera controller, or PXP.** The package pin names and Forlinx workbook still show `LCDIF_*` and `CSI_*` mux labels inherited from the RT1060 family/pin-compatible RT1062. Those labels are retained below to make the source documents traceable, but they are not working LCD/camera functions on an RT1061.

### Complete exposed UART routes

UART1 and UART2 are the only connector-designated UARTs, but they are **not** the only UARTs available. Joining the 100-pad connector to the NXP mux table gives seven complete LPUART TX/RX routes. Every signal below is unbuffered, non-isolated, nominal 3.3 V MCU logic; none is RS-232 or 5 V tolerant. Configure both the pad mux and the corresponding input daisy selector.

| LPUART | TX SoM pad | RX SoM pad | Optional flow control | Principal conflicts / notes |
|---|---:|---:|---|---|
| LPUART1 | 24 | 23 | CTS 15, RTS 14 | Connector-designated debug UART. CTS/RTS collide with the CAN2/CAN-FD pair; pad 15 is also ADC-capable. |
| LPUART2 | 12 | 13 | CTS 9, RTS 8 | Connector-designated UART2. Flow control collides with designated I2C1. |
| LPUART3 | 7 | 6 | CTS 96, RTS 99 | TX/RX use legacy CSI-labelled GPIO. Flow-control pads also have USDHC2/legacy CSI aliases. |
| LPUART4, route A | 57 | 59 | Not exposed as a matching four-wire group | Collides with Ethernet-MAC-2 receive signals. |
| LPUART4, route B | 80 | 81 | Not exposed as a matching four-wire group | Collides with the connector-designated FlexSPI-B/SD2 group. Select the correct LPUART4 RX daisy for this route. |
| LPUART5 | 16 | 18 | No matching exposed CTS/RTS pair | Electrical mux exists, but Forlinx explicitly reserves pad 18/D14 for the core-board watchdog-reset signal and says not to reuse it on a carrier. Do not select this route without written confirmation. |
| LPUART6 | 29 | 28 | No matching exposed CTS/RTS pair | The OK1061-S uses these nets as Ethernet-PHY resets; pad 29 is also connector-labelled PWM0. They are free for UART on a custom carrier that omits those uses. |
| LPUART8, route A | 73 | 72 | CTS 69, RTS 68 | Complete four-wire option, but it consumes part of the designated USDHC1 bus. Select the route-A RX/CTS daisies. |
| LPUART8, route B | 97 | 95 | No matching exposed CTS/RTS pair | Uses legacy CSI/keypad/ADC-capable pads. Select the route-B RX daisy. |

Pad 47 also offers an LPUART8 RX alternate but has no corresponding exposed TX in that pad group. No complete LPUART7 TX/RX pair is exported. This is why Forlinx advertises up to seven UART instances even though the RT1061 contains eight. Forlinx quotes a hardware ceiling of 5 Mbit/s; achievable rate depends on the selected root clock, baud divisor/error, I/O loading, isolation components, and carrier routing.

- **MCU pad** is the NXP IOMUXC pad name; **ball** is the BGA coordinate on the MCU.
- **SoM signal** preserves the Forlinx manual/schematic name where useful.

## Complete MCU alternate-function matrix for connected signal pads

This is the historical Forlinx workbook's `ALT0`…`ALT10` matrix joined to the SoM pad numbers by MCU ball, except for explicit corrections against current NXP IOMUX definitions listed in [Known documentation errors, conflicts, and corrections](#known-documentation-errors-conflicts-and-corrections). Blank modes are omitted, but the exact ALT number is retained. ADC and comparator routes are shown separately because they are analog assignments rather than ordinary digital mux modes.

Important qualifications:

- `CSI_*` and `LCDIF_*` entries are package/family mux labels but the RT1061 has no CSI or LCDIF peripheral; do not select them expecting a working camera/display controller.
- The workbook preserves the legacy Forlinx routing/provenance. Current exact-part NXP IOMUX definitions and the reference manual are authoritative for mux modes, daisy-chain input selection, pad control, electrical limits, and whether a peripheral instance exists on RT1061. Known workbook deviations are recorded under [Known documentation errors, conflicts, and corrections](#known-documentation-errors-conflicts-and-corrections).
- Names such as `LPI2C1_SCLS`, `LPI2C1_SDAS`, `ENET2_TDATA*`, and `ENET2_RDATA*` are reproduced exactly from the workbook.
- Pins 77–81 are labelled FlexSPI B on the connector/schematic, while the workbook's Forlinx-default column calls them GPIO. FlexSPI B is ALT1 on these pads.
- The onboard NOR occupies non-exported `GPIO_SD_B1_06`…`GPIO_SD_B1_11` balls as FlexSPI1 Port A: L3 `SS0_B`, L4 `SCLK`, and P3/N4/P4/P5 data 0…3. `FLEXSPI_A_*` alternatives on exported pads are alternate routes for that same boot-flash port, not an independent flash interface; changing its mux, daisy, clock, or controller configuration can stop XIP/boot. FlexSPI2's `GPIO_EMC_23`…`GPIO_EMC_29` group is not exported. The exposed Port-B group can also share controller resources, so change FlexSPI configuration only from XIP-safe code.
- The vendor BSP assumes its selected default pin functions. Remuxing a pad may silently conflict with an enabled vendor driver even when the electrical route is valid; audit the complete firmware pin configuration.
- Native USB pads 83–88 are dedicated and therefore have no IOMUX alternatives.

## Reset states, pulls, boot straps, and power sequencing

### Documented module-level pulls

The Forlinx manual **reports 10 kΩ pull-ups on the SoM** for:

- Pin 48: `BOOT_MODE0`
- Pin 49: `BOOT_MODE1`
- Pin 52: `BT_CFG6`
- Pin 53: `BT_CFG7`
- Pin 54: `BT_CFG9` / `ENET2_TX_DATA1`
- Pin 55: `BT_CFG8` / `ENET2_TX_DATA0`
- Pin 56: `BT_CFG10` / `ENET2_TX_EN`
- Pin 61: `BT_CFG11` / `ENET2_TX_CLK`

These are sampled during reset. Do not allow PHYs, LEDs, strong external pulls, or other carrier loads to override the intended strap levels. The old manual's pull table contains duplicate/missing pad numbers; the exposed-pad list above has been reconciled against the connector pinout and MCU pad names. Because no SoM schematic is present, verify the actual resistor population and boot levels on the module revision being used. The same damaged source table also claims pulls on several non-exported boot/flash signals, so it is not a reliable full resistor BOM.

### MCU-internal reset states

The NXP electrical data for the 10 × 10 mm package gives these silicon reset states:

- Most exported `GPIO_AD_B0/B1`, `GPIO_B0/B1`, `GPIO_EMC_39..41`, and `GPIO_SD_B0/B1` pads reset as inputs with keeper enabled, subject to the boot/debug exceptions below.
- `BOOT_MODE0` (pin 48) and `BOOT_MODE1` (pin 49) have 100 kΩ internal pull-downs. Forlinx's stronger 10 kΩ module pull-ups dominate if populated as documented.
- Pads 52–56 and 61 (`GPIO_B0_10`…`GPIO_B0_15`) have a normal/default GPIO setting of input/keeper. On reset while sampled as `SRC_BT_CFG6`…`SRC_BT_CFG11`, they are inputs with 100 kΩ internal pull-downs; the reported module 10 kΩ pull-ups dominate if populated.
- Current NXP reset states are: TMS, TDI, and TRSTB inputs with 47 kΩ pull-ups; TCK input with 100 kΩ pull-down; JTAG_MOD input with 100 kΩ pull-down; and TDO three-state/output with keeper.
- `PMIC_ON_REQ`, `POR_B`, `WAKEUP`, and `ONOFF` are in the `VDD_SNVS_IN` domain and have 100 kΩ internal pull-ups.

Forlinx states that the assembled SoM holds `JTAG_MOD` down and recommends SWD, which agrees with the current NXP reset state. Some older electrical material can be read as a 100 kΩ pull-up; use the current exact-part data sheet for silicon behavior and verify the actual module if an external strap matters to the design.

### Reset and carrier-power behavior

- Pin 20 `POR_BUTTON` enters the on-module reset/power circuit. Pulling it low cuts/reset-cycles the SoM supply path according to the manual.
- Pin 21 `POR_B` is the MCU's direct active-low power-on-reset input; the manual permits it to be left unconnected if unused.
- Pin 17 `PMIC_ON_REQ` is an active-high output intended to enable carrier power after the SoM has started. The OK1061-S uses it to sequence the SoM before carrier peripherals and reduce latch-up risk.
- Pin 66 `ONOFF` is the boot/on-off button input; the manual permits it to be left unconnected if unused.
- Pin 65 `WAKEUP` can be the wake input or `GPIO5_IO00`.

### SWD/JTAG wiring, debugger reset, and VTref

Use the following minimum SWD connection. `POR_B`, not `POR_BUTTON` or `JTAG_TRST_B`, is the debugger's system-reset signal.

| Debugger signal | FET1061-S connection | Requirement / reason |
|---|---|---|
| SWDIO | Pad 33, `JTAG_TMS/SWD_DIO` | Bidirectional nominal 3.3 V logic. |
| SWCLK | Pad 32, `JTAG_TCK/SWD_CLK` | Keep the trace short and referenced to ground. Reduce probe clock during first bring-up. |
| nRESET | Pad 21, `POR_B` | Direct active-low MCU power-on reset. Use a probe output compatible with an active-low/open-drain reset node; it must not drive high against the on-module supervisor. |
| Ground | One or more SoM ground pads / carrier ground near the debug header | Give the probe a short, low-inductance return; include more than one ground in a ribbon header where practical. |
| VTref | A sense-only carrier 3.3 V described below | Probe input only; this module provides no connector pin for its internal main I/O supply. |
| TDO/SWO, optional | Pad 35, `JTAG_TDO` / `ARM_TRACE_SWO` ALT9 | Optional trace output where supported by the selected debug mode/tool; configure the SWO mux and trace clock. Not required for basic SWD. |

Do **not** connect the debugger reset output to pad 30 `JTAG_TRST_B`; that resets the JTAG test-access port rather than the whole MCU. Do **not** use pad 20 `POR_BUTTON` as ordinary SWD reset; it enters the module-level power/reset path and removes/reset-cycles module power according to Forlinx.

None of the 100 pads is documented as an output from the SoM's main 3.3 V I/O rail. Pin 27 is a backup-domain input, and USB VBUS pins 83/86 are 5 V nodes. A production carrier can provide a **sense-only 3.3 V VTref proxy** from a carrier regulator powered whenever the SoM's 5 V input is powered. It must connect only to the probe's VTref input; it does not get tied to any hidden module rail and must not be allowed to back-power an unpowered SoM through SWDIO, SWCLK, or reset. Because this proxy does not detect an internal SoM-rail fault or startup delay, the probe must not drive SWD until module power is known valid. A verified actual SoM-I/O-rail sense/test point or a qualified power-good/buffer arrangement would be preferable if Forlinx provides/supports one. Verify whether the exact probe's pin labelled `3V3`/`VCC` is an input, an output, or configurable before connection. Some probes can use an internally configured fixed 3.3 V reference, but that is tool-specific.

### Boot-source notes

The SoM exposes only part of the MCU boot-configuration field directly. The OK1061-S manual uses four DIP positions around `BOOT_MODE[1:0]` and `BT_CFG[7:6]` and gives these carrier settings:

| OK1061-S DIP setting | Documented purpose |
|---|---|
| 1 OFF, 2 OFF, 3 OFF, 4 OFF | QSPI NOR boot |
| 1 OFF, 2 OFF, 3 ON, 4 OFF | SD/TF-card boot |

Those switch positions are carrier-specific, not a substitute for the NXP boot-mode table when designing a custom carrier. The software package also contains serial-download/flashloader and IAP material. No verified fitted QSPI NAND exists despite the old manual mentioning a NAND boot option.

## Custom-carrier minimum-system and layout checklist

The old Forlinx manual says the SoM can start with only 5 V, reset, and boot configuration, but also recommends fitting a debug interface so successful boot can be observed. For a robust carrier:

1. Feed both `5V_SYS` pads from a clean 4.5–5.5 V source sized for the SoM and all carrier loads. There is no authoritative module-current maximum in the supplied/public documentation, so measure a representative worst-case application and retain margin.
2. Connect every ground pad with short, low-inductance returns. Do not omit grounds merely because there are many duplicates.
3. Generate carrier peripheral 3.3 V locally; the SoM does not export its main I/O supply. Sequence or isolate externally powered signals so they cannot back-power an unpowered module.
4. Provide SWDIO pad 33, SWCLK pad 32, `POR_B` pad 21, ground, and a sense-only VTref at an accessible debug header. Clearly distinguish a probe's voltage-reference input from any target-power output. Keep `POR_BUTTON` separately accessible if a full module power/reset cycle is useful.
5. Keep reset-sampled boot pads free of loads that defeat the documented pulls. This is especially important where Ethernet 2 shares boot pads.
6. Use `PMIC_ON_REQ` if carrier peripherals need sequenced power; it is not a high-current rail.
7. Supply `VDD_COIN_3V3` only if SNVS/RTC retention is required and observe the NXP backup-domain limits. It is an input, not a carrier supply.
8. Add external I²C pull-ups. The OK1061-S uses 4.7 kΩ to 3.3 V; recalculate for bus capacitance and speed.
9. Add PHYs/magnetics for Ethernet and transceivers/termination/protection for CAN/CAN-FD.
10. Add USB connector VBUS switching/current limiting, ESD protection, and controlled-impedance differential routing. Treat pins 83/86 as USB VBUS nodes, not convenient 5 V outputs.
11. The MCU's SD/EMC banks can support 1.8 V or 3.3 V at silicon level, but the reference FET/OK use is nominally 3.3 V and no SoM schematic is supplied. Verify the actual module rail before attaching 1.8 V devices or applying external voltage.
12. Observe the on-SoM LED load on pad 31 when using JTAG TDI, SAI2 TX data, or GPIO1_IO09.
13. Review every muxed group as a whole, including input daisy selection. Selecting a pad's ALT mode alone may not route a peripheral input correctly.
14. Keep analog inputs within their ADC supply range, use a quiet ground/reference strategy, and validate source impedance, acquisition time, protection leakage, and conversion settling.
15. Treat any isolated interface as a complete subsystem: provide isolated-side power, maintain creepage/clearance and separated grounds, and validate the assembled path rather than relying only on the isolator IC name.
16. Lock the clock/DCDC configuration to the actual `CVL5A` or `CVL5B` suffix and verify the software time base at run time. Do not inherit stale clock constants from example BSPs.
17. Use NXP's current i.MX RT1060 hardware-design guide for power, USB, Ethernet, SD, crystal, EMC, and high-speed-routing details; the module manual is not a complete signal-integrity guide.

Carrier-only conflicts in the reference OK1061-S do not necessarily exist on a custom carrier. Examples include CAN2_TX versus the adjustable ADC source, SD versus the SPI header, camera/keypad sharing, and JTAG pins versus audio population/jumpers.

## Known documentation errors, conflicts, and corrections

1. The hardware manual's cover is FET1061-S/OK1061-S, but its warning page and PDF metadata reuse `OK335xD` text.
2. The cover/update record says January 2019; the PDF file metadata shows creation/modification in December 2020.
3. The manual says both QSPI NAND and NOR are mounted. The board photo, board-specific software, bare-metal manual, and current product page verify NOR only. Do not add NAND to a BOM without Forlinx confirmation.
4. Flash evidence spans a photographed/configured 4 MiB W25Q32, a bundled W25Q64 data sheet and generic EVK 8 MiB configuration, and a current 16 MiB ordering option. Read the fitted flash marking and set the boot header accordingly.
5. The detailed manual table covers only pads 1–80; pads 81–100 had to be recovered from the connector image and carrier schematics.
6. The manual's NET2 table mistakenly repeats NET1 MCU balls. Correct pins 54–61 are D10, C10, E10, A11, D11, B11, C11, and E11.
7. The manual describes `ENET_TX_CLK` pins 44/61 as outputs. NXP's electrical data defines them as inputs.
8. Pins 45–47 are the connector-designated SEMC/GPIO expansion group. Ethernet MDIO/MDC on 45/46 is only an alternate; both reference-carrier PHYs actually share pins 62/63.
9. Pins 77–81 are connector-labelled FlexSPI B, but the workbook's Forlinx-default column labels them GPIO; FlexSPI is ALT1.
10. Several carrier audio aliases say `SAL1`/`SAI1` where the actual pad mux is SAI2 on pins 31, 34, 35, 48, and 49.
11. The manual says the assembled module holds JTAG_MOD down. Current NXP Rev. 4 agrees and specifies a 100 kΩ reset pull-down; older electrical material suggesting a pull-up is stale for this purpose.
12. The manual's boot-pull table contains missing/duplicated pin numbers and cannot override the reconciled connector mapping.
13. The manual refers to a minimum-system schematic in Appendix 3, but it is Appendix 2 on page 37.
14. The bare-metal manual's running headers incorrectly name FET1052-C/OK1052-C, and its software tree contains inherited RT1050/1052/RT1060-EVK statements.
15. The historical mechanical DXF/STEP filenames/internal labels are generic or mismatched. They are not an independently verified FET1061-S production land-pattern package.
16. The pinmux filename says 2019-04-12 while the workbook's internal modification date is 2019-05-20.
17. The shared carrier preserves camera circuitry and `CSI_*`/`LCDIF_*` names, but RT1061 has no CSI, LCDIF, or PXP. Those functions exist on pin-compatible RT1062-family variants, not this MCU.
18. Old/current resource counts differ because some are routed-module counts and others are raw MCU capability: SAI 2 versus 3, UART 7 versus 8, ADC 10 versus 20, and QSPI 1 versus 2 are prominent examples.
19. The module's −40 to +85 °C operating rating is not the same metric as the MCU's −40 to +105 °C junction-temperature range.
20. The later public BSP's `CVL5B` and the photographed/manual board's `CVL5A` require different NXP silicon errata. Inspect the chip.
21. The bundled RT-Thread clock source says 600 MHz in constants/comments but actually configures 528 MHz (`24 MHz × 88 / 2 / 2`) and sets a nominal 1.275 V core target, above the current `CVL5x` 1.26 V operating maximum. It is not proof that the module ran at 600 MHz and can give software the wrong time base.
22. No main 3.3 V supply output exists in the documented 100-pad connector. `VDD_COIN_3V3`, USB VBUS, and the internal flash VCC must not be reinterpreted as general carrier-power pins.
23. The old Forlinx workbook places `FLEXCAN3_TX` at ALT9 on pad 35 and omits SWO. Current NXP IOMUX definitions put `FLEXCAN3_TX` at ALT8 and `ARM_TRACE_SWO` at ALT9 on the same physical JTAG-TDO pad; this document uses the current NXP mapping.

## Production-use verification

Before freezing a custom carrier or firmware image, record the actual module's:

- PCB revision/silkscreen.
- MCU suffix (`CVL5A` or `CVL5B`) and applicable NXP errata.
- Flash marking/capacity and the matching FlexSPI boot configuration block.
- Actual run clock, bus divisors, `VDD_SOC` DCDC target, and correct `SystemCoreClock` reporting.
- Measured module peak current in the intended clock/peripheral/temperature workload.
- Actual boot-strap resistor population and reset levels.
- Actual SD/EMC I/O-bank voltages.
- Carrier 3.3 V generation/sequencing and proof that no external interface back-powers the module.
- SWD reset/VTref polarity and whether each debug-header power pin is a sense input or a source.
- Mechanical dimensions, pad geometry, paste aperture, component clearance, and reflow profile from an approved Forlinx drawing.

Application-specific interface, isolation, analog-input, clock, and boot checks live in [Application verification](../application/verification.md).

Forlinx's full SoM schematic and BOM are not present in this repository. Obtain them—or written confirmation of the relevant unknowns—before relying on unidentified power/reset parts or a generic family mechanical model.
