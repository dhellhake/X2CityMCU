# DD-001 — Software unit design

**Draft vehicle baseline — 2026-09-16.** Complete vehicle policy, input, traction and platform unit contracts are retained.

**Draft 1.3 — 2026-09-14; successor to DD-001-R1.1.** This controlled refinement defines the Hall-position/FOC-control units for the selected EVM traction-board and WeAct vehicle-host boundaries. It implements no code, makes no physical-control claim, and does not revise approved requirement bodies.

## Scope and modelling rules

Each `U-*` unit has one owning `SC-*` component. Unit Requirements derive only from an Abstract Software Requirement .ASW); no Unit Requirement derives directly from System, HSI, FSC, or hardware requirements.

Every local record carries a semantic value, qualification, freshness, producer identity, configuration, and reset/operation context. A consumer accepts it only if all are current, coherent and qualified; absent, stale, invalid and context-mismatched values remain unavailable. A command, acknowledgement, status bit or zero request never proves a physical state. Inputs are immutable snapshots and state/output updates are atomic.

The DRV8300DRGE-EVM and WeAct STM32H723VGT6 are selected vehicle traction-board baseline and host, respectively, but no adapter pin map, task rate, timeout, calibration, diagnostic coverage or physical output is selected. The selected Hall-sensored FOC realization is defined in [MCD-001].../../Motor/MCD-001_Hall_Sensored_FOC_Technical_Design.md), its [EVM integration contract].../DRV8300DRGE-EVM/DRV8300DRGE-EVM_Integration_and_Requirements_Fit.md) and its [WeAct host contract].../../STM32H723VGT6/WeAct_STM32H723VGT6_Vehicle_Controller_Integration.md); timing/calibration/protection gates remain open. Existing firmware remains development evidence, not final-product acceptance.

## Vehicle policy units

### U-SET-STATE

Consumes qualified current-context VD18MT requests and coherent qualified standstill/physical-accelerator-rest evidence. It retains distinct requested, pending and active state. On an interpretable speed request `r`, it applies the parent normalization `N.r)=r` for `0<r<40` km/h and `N.r)=40` for `r=0` or `r>=40`; unrecognized input changes neither valid active nor pending state. The latest valid pending settings apply atomically only when both guard facts hold. Active values remain otherwise, and active/pending speed never exceeds 40 km/h. After HMI loss, it may publish a current retained active-state snapshot with the original receipt provenance; HMI absence does not by itself age out a valid active selection or refresh the receipt. No received setting is inferred from initialization, retention, absence or an unqualified receipt.

### U-SESSION-ELIGIBILITY and U-SESSION-REPORT

Eligibility starts ineligible in each new vehicle context. Only the complete parent Ready guard issues an authority token with current context and expiry; any absent, invalid, expired or mismatched prerequisite withdraws it. A recognized parent-defined riding fault latches current-session inhibition, which cleared observation alone cannot remove. The unit consumes self-test results and does not claim their diagnostic coverage or physical inhibition.

Report selection starts empty per context. With no selection, retain the earliest recognized reportable group fault; for an indistinguishable earliest set retain the lowest assigned code. Retain it until restart, above low-charge `0x01`; it cannot rank physical severity, clear inhibition or establish display receipt.

### U-DEMAND-ARBITER

`U-DEMAND-ARBITER` is the one `SC-DEMAND.V` policy decision point. It consumes separately typed snapshots, never a heterogeneous collection: `AcceleratorPositionV1`, `BrakeStateV1`, `ActiveRidingSettingsV1` (the dedicated active projection; pending settings are excluded), `RidingAuthority`, `BatteryCapabilityEnvelope`, `QualifiedMotionV1`, `ActualTractionOutputV1`, current platform context/health, and immutable active resolved `DemandPolicyCalibration` data. It emits `WheelTorqueRequest` and a service-only `DemandPolicyDiagnostic`; it neither activates settings, creates Session authority or a fault latch, evaluates battery protection, nor applies FOC/output control.

The command has `requestedWheelTorqueNewtonMetres: Real`, signed at the rear wheel: positive is forward propulsion and negative is regenerative braking. It carries `authorityGeneration`, `decisionSequence`, `decisionTimestampTicks`, `commandExpiryTimestampTicks`, `commandClockId`, `commandClockContextId`, producer/context and configuration identity, qualification/freshness, and decision reason. Authority carries its own decision sequence/timestamp, expiry timestamp and clock/context. The command expiry timestamp is independently evaluated from authority expiry; matching authority generation is necessary but never extends either expiry. `U-TRACTION-ACCEPT` emits an accepted record only when the authority and command clocks/contexts are equal or their timebase conversion is qualified, with `effectiveAcceptedExpiryTimestampTicks=min(authorityExpiryTimestampTicks, commandExpiryTimestampTicks, acceptanceFreshnessBound)`; `U-TRACTION-CONTROL` rechecks that effective expiry in its accepted clock/context. A record is usable only when every required common contributing record is qualified, fresh, same current vehicle/reset generation, configuration-compatible, on the named clock/context and coherent at the declared decision snapshot. Any common producer, context, configuration/calibration or platform-health invalidation withdraws the prior command and diagnostic atomically; an unavailable sign-specific battery branch instead only withdraws its own sign and is not represented by its last value.

The arbitration is a bounded clamp, with separate non-negative propulsion and non-positive regeneration permissions. Pedal request maps through the active level profile to positive wheel torque. Level 0 allows no regeneration. Levels 1–5 use the parent provisional neutral at 35%; the resolved calibration supplies their full and same-positive endpoints, ramps, taper and response parameters and is unusable when profile activation is not permitted. A lever blocks positive torque only; it may still permit accelerator-requested regeneration under the profile. The active speed limit and hard 40-km/h cutoff constrain both signs. `BatteryCapabilityEnvelope` carries independently qualified positive and negative branches, each with its own torque/speed ceiling, reason and restriction generation: a low-SOC positive branch constrains positive torque only, and an unavailable negative branch constrains only negative torque while a current positive branch remains usable. Fault/authority withdrawal, missing common rider/motion/profile evidence, and every both-sign parent inhibition command zero. The approved 5-level exception omits comfort smoothing, but still applies the qualified low-speed taper. Demand does not manufacture a new rider choice, numerical threshold, ramp or taper.

Post-stop regeneration is a Demand-owned rearm state, initially disabled for each vehicle context and after qualified standstill. It remains disabled through hand-push movement. It re-arms only after the current `ActualTractionOutputV1` provides qualified evidence of forward travel together with qualified **positive applied wheel-torque** evidence in the same context/configuration; a commanded positive value, PWM state, Hall state/edge, speed alone, or a zero request cannot re-arm it. This rearm episode is separate from Demand's regenerative-restriction recovery episode: on each qualified partial or full negative-capability reduction, Demand retains the reduced negative ceiling under that new episode generation. While the scooter remains moving and the accelerator remains continuously in the regenerative range, a later negative-capability clearance or partial relaxation alone cannot increase the held ceiling. Leaving the regenerative range or qualified standstill qualifies that episode before **or after** clearance; once both episode qualification and current qualified clearance/relaxation exist, Demand recovers automatically, including at standstill. Battery policy supplies the branch and its restriction generation, but does not own this rider/motion episode, Session fault restart, or post-stop rearm.

For one decision snapshot, precedence is deterministic: (1) context/reset, platform-health, qualification/freshness/coherency failure in common rider/motion/profile evidence, expired or generation-mismatched authority, and both-sign parent inhibition withdraw both signs; (2) hard 40-km/h cutoff, active speed limit and qualified both-sign limits constrain both signs; (3) the post-stop/hand-push regeneration rearm gate, the Demand-owned recovery hold, and the negative capability branch constrain **negative** torque only; (4) lever and the positive capability branch constrain **positive** torque only; (5) the active-level pedal/profile request and low-speed taper are clamped to the remaining sign-specific envelopes. A branch invalidation never enlarges its sign and does not invalidate the other current branch. If a simultaneous event withdraws a restriction while any tighter inhibition is present, the tighter inhibition wins; a recovery/increase never takes effect before the withdrawal/invalidation result in that snapshot. Equivalent sources must declare the same snapshot/coherency epoch; otherwise the decision is unavailable/zero, not ordered by transport arrival.

`DemandPolicyCalibration` is a configuration dependency, not an implicit constant. Its resolved release record carries the level maps, full/end-point correspondence, neutral point, speed/taper shape, ramps, reference limits and symbolic response parameters used by the decision; `profileActivationPermitted=false`, missing, malformed or unvalidated fields make the profile unavailable. Their numerical values, bounds, units, owner, review state and verification are an end-to-end engineering gate: the calibration owner must release each parameter with the matching input qualification and traction acceptance/physical-response verification. Until that happens, the design is **not implementation-ready** and must not claim a response time, ramp, taper, numerical speed threshold or physical torque tracking bound. The diagnostic output reports unavailable/zero/restricted reason, branch/recovery-episode and decision generations for service only; it creates no rider indication and has no control return path.

### U-HMI-ADAPTER and U-LIGHT-MODE

The HMI adapter distinguishes current qualified receipt from decoder initialization, retained setting and transport activity. Endpoint loss, restart or unqualified receipt creates no setting or authority. Each outgoing update forms only parent-defined fields from selected report, usable charge and unsigned current magnitude/fallback, preserving internal validity separately from a transmitted fallback. Encoding, rounding, timing, electrical transport and display presentation remain gates.

Light mode starts normal request `N` Off in each powered session and retains it through communication loss. Front follows `N`; rear is Full for an actuated lever, active electrical braking, or either unqualified fact, otherwise Dim for `N=On` and Off for `N=Off`. It publishes logical intent only; physical conservative rear behavior before policy execution remains hardware/system work.

## Input, traction and platform derivation gates

`U-ANALOG-ACQ-REGULAR` owns completed regular scans; `U-ACCELERATOR-QUALIFY` and `U-BRAKE-QUALIFY` alone convert them into the typed rider records consumed by Settings, Session, Demand and Light. `U-HALL-CAPTURE` owns current sampled-state/edge evidence and capture health, and `U-HALL-POSITION` publishes electrical position only with accepted map/alignment. `U-MOTOR-PHASE-FAST` and `U-SUPPLY-FAST` publish current same-operation phase-current and Vdc evidence; they do not use regular scans or historical values. These seven units invalidate their own result on producer/reset/configuration/health failure and preserve no prior value as a substitute. `U-TRACTION-MOTION` is the sole detailed producer of `QualifiedMotionV1` for Demand, Settings and Session: it publishes vehicle speed, travel direction and standstill independently of Ready and command acceptance only by interpreting current Hall capture/position evidence with capture health, map/pole-pair/final-drive/loaded-wheel calibration and a released bounded-observability/standstill criterion. These calibration, capture-health and timing/uncertainty criteria are named engineering gates; until they are accepted, it publishes Unknown/unavailable. A static Hall state, an absent edge alone, command or output-enable state is not vehicle motion. `U-TRACTION-ACTUAL-OUTPUT` produces `ActualTractionOutputV1` as a qualified applied-wheel-torque **estimate** from current post-stage physical facts with source/timestamp provenance plus same-operation phase-current/position and qualified vehicle-motion evidence, using released `ActualOutputEstimationCalibration`; it runs during startup, disarmed and withdrawn states as an observation function. `U-TRACTION-ACCEPT` evaluates authority/command acceptance separately and cannot gate, refresh or manufacture that observation. `actualAppliedWheelTorqueNewtonMetres`, active electrical braking and powered-forward-travel are unavailable if any estimator evidence, calibration or generation match is absent; a requested command, FOC reference, acceptance result, CCR/PWM state or output-stage event alone is insufficient. These observations are never proof of physical torque, braking or energy direction. `U-TRACTION-CONTROL` consumes only a current accepted signed demand, independently rechecks its effective expiry/context, and uses the selected FOC realization to form `PWMAndADCSamplingPlanV1` including the next `CCR1..3`, `CCR4` sampling plan and ADC context. `U-TRACTION-OUTPUT` alone performs the guarded literal register stage/commit and publishes current physical-stage evidence independently of new command acceptance, including startup/disarmed/withdrawn state. `U-PLATFORM-CONTEXT` creates/invalidate contexts and orchestrates startup; `U-PLATFORM-BINDING` owns project peripheral/vector/DMA binding, the static shared fast-resource wrappers, bounded PRIMASK/barrier contract and routes each vector to its named unit; `U-PLATFORM-RETENTION` restores only host-provided items after integrity/context qualification; `U-PLATFORM-HEALTH` publishes scheduling/local-health events without asserting a safe physical reaction.

These are explicit SW realizations in ARCH-003 and support HSI-001/004/007/009. `U-ANALOG-ACQ-FAST`, `U-TRACTION-CONTROL` and `U-TRACTION-OUTPUT` implement the completed fast-epoch, command-data and literal latch sequence defined by the [allocated traction HSI](../DRV8300DRGE-EVM/DRV8300DRGE-EVM_WeAct_STM32H723VGT6_Traction_HSI.md) and [runtime integration contract](../SoftwareArchitecture/Runtime_Integration_Contract.md). The latter distinguishes project bindings from generic drivers and direct fast calls from scheduled routes. Their distinct ASW requirements and Unit children are recorded in the Control Unit Requirements catalogue. Electrical/sensing, command representation, response bounds, host resources, reset domains, retention integrity, physical outputs and diagnostic coverage remain parent acceptance gates.

## Traceability and verification intent

The catalogue and [Control Unit Requirements].../../Requirements/Unit_Requirements/Control_Unit_Requirements.md) provide stable unit→SC and ASW→UR mappings; each UR names its parents. Planned unit verification covers state transitions, unavailable/stale/context mismatch, reset and simultaneous-event cases. It is not executed evidence. Parent System requirements retain their stated-level verification including physical output and end-to-end timing.
