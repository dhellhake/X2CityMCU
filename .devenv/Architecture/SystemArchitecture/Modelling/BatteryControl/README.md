# BatteryControl

`LE-BATTERY-CONTROL` is an `LE-EPCS` child. It contains the owner-built physical `BatteryAssembly` (`Cells` plus the supplied `Bms` hardware and vendor firmware) and the vehicle-host `BatterySupervision` logical responsibility for reading and qualifying BMS information and determining capability. The energy wrapper is retired; `LE-ENERGY-PATH` is an EPCS sibling. BatteryControl supplies qualified battery information and capability; it does not own motor-controller enforcement or vehicle-wide physical protection.

## Decomposition and required information contracts

```mermaid
flowchart LR
  EPCS[LE-EPCS] --> BC[LE-BATTERY-CONTROL]
  EPCS --> EP[LE-ENERGY-PATH]
  BC --> PBA[BatteryAssembly]
  PBA --> Cells[Cells]
  PBA --> Bms[Bms: supplied HW + vendor FW]
  BC --> BS[BatterySupervision: project SW]
  Bms -->|battery observations| BS
  Cells <-->|cellPower / cellGroupTaps| Bms
  Cells -->|packThermalObservation| Bms
  BS -->|batteryStatusOut| RidingControl[LE-RIDING]
  BS -->|batteryOperatingLimitsOut| RidingControl
  BS -->|stateOfChargeOut| HMI[LE-HMI]
  BS -->|stateOfChargeOut| RidingControl
  BS -->|batteryCurrentOut| HMI
  BC <-->|batteryPower| EP
```

`BatteryMeasurements` projects these source fields only after fieldwise validity, consistency, source-timeliness qualification and other required evidence; each value has an independently named qualification indication. Source-update timers and timing references remain private to BatterySupervision and are not published alongside observations. No BMS measurement timestamp is inferred from host receipt time. Raw BMS RSOC/capacity is only `stateOfChargeCandidatePercent` until BMS-002/BMS-003 and the SOC policy qualify actual SOC. A UART value, FET/path bit, or project-software limit does not prove physical isolation or protection; the EPCS duties in BMS-004/005/009 remain applicable.

## Requirement composition and derivation

The current catalogue contains 310 canonical requirements, including 46 numbered native usages held in their owning component files and composed through eight unnumbered architecture collections. Native SysML `require QualifiedPackage::canonicalUsage;` references provide conjunctive composition under SysML 2.0 §7.21.2; each referenced usage retains its canonical subject and body ([SysML 2.0 Language](https://www.omg.org/spec/SysML/2.0/Language/PDF)). The collections add no catalogue records. BatterySupervision owns 35 of those numbered usages. The model has 54 satisfaction assertions, 97 required references, and a distinct 47-edge requirement-derivation graph. Satisfaction assertions express design intent, not verification evidence; composition expresses coverage and does not create derivation edges.

```mermaid
flowchart TB
  BC[BatteryControl collection<br/>own six canonical requirements] --> BA[BatteryAssembly collection<br/>own BATASM-001]
  BC --> BS[BatterySupervision collection<br/>own BMSIF-001–003 and 005–014, BMSPOL-001, BATSUP-001–016]
  BA --> Cells[Cells collection<br/>own CELL-001]
  BA --> Bms[Bms collection<br/>own BMSDEV-001–003]
```

The single per-startup nominal-capacity snapshot is captured once at controller startup and retained for that controller cycle. [BATSUP-007–011](Decomposition/BatterySupervision.sysml#req-sys-batsup-007) define regenerative capacity, temperature and voltage ceilings; [BATSUP-012–015](Decomposition/BatterySupervision.sysml#req-sys-batsup-012) define the corresponding discharge ceiling, using `IbD = 1.00 × C_Ah`, its specified temperature factor and the minimum qualified group-voltage bound. Both tapers use [BatterySupervision.voltageDeratingCalibration](Decomposition/BatterySupervision.sysml#req-sys-batsup-016); qualification and its symbolic formulas are canonical there. Each direction uses its own applicable temperature/voltage envelope and path state; SOC, system fault, protection, component and physical limits remain independent constraints. Cells at or below −5°C yield zero discharge ceiling; owner-selected cold use therefore requires a sufficiently warm battery for propulsion while retaining −10…+40°C E/E startup conditions ([DEC-BAT-002](../../../../Requirements/DEC-001_Decisions_and_Open_Issues.md#dec-bat-002), [OI-051](../../../../../README.md#15-unresolved-issues)).

The component collections mirror `BatteryControl → (BatteryAssembly, BatterySupervision)` and `BatteryAssembly → (Cells, Bms)`. The three assembly contribution collections bridge individual parent obligations through the immediate architecture child: selection, commissioning configuration and source information. BatteryControl requires the assembly and supervision collections; the BatteryAssembly collection requires its canonical BATASM-001 requirement plus the Cells and Bms collections. Parent requirements also require the relevant bridge and supervision contributions: BAT-002 requires `assemblySelectionRequirements`; BMS-002 requires `assemblyConfigurationRequirements` and BMSIF-005 basic-field decoding; BMS-003 requires `assemblySourceInformationRequirements`, BMSIF-001–003, BMSIF-005–008, BMSIF-009–014 and BATSUP-003; BMS-006 requires BATSUP-001/002, BMSIF-005 basic-field decoding and BMSPOL-001; BMS-007 requires BMSPOL-001 and BATSUP-004–021; BMS-008 requires BMSPOL-001. These purpose-selected `require` references compose coverage and do not create derivation edges or architectural children. BMSIF-003 defines response-envelope conditions for measurement updates; BMSIF-014 adds outstanding-request correlation and success-status conditions; BMSIF-005–008 and related field requirements own schema and value decoding/qualification. The BMSIF behavioral rules are canonical in BatterySupervision.sysml; [BMS_Information.md](Decomposition/BMS_Information.md#selected-unit-uart-read-acceptance-contract) retains protocol facts and verification guidance, not a separate acceptance contract.

The existing parent-to-child `#derivation` connections in [BatteryControl.sysml](BatteryControl.sysml) use the standard `RequirementDerivation` domain library ([SysML 2.0 Language, §9.6](https://www.omg.org/spec/SysML/2.0/Language/PDF)), which the model workspace must load. The 47-edge graph remains the distinct provenance/contribution DAG: the BMSIF and BATSUP children derive from their System Requirement parents, without Abstract Software to Abstract Software derivation; it need not mirror the architecture branches, and a source citation is not a derivation.
