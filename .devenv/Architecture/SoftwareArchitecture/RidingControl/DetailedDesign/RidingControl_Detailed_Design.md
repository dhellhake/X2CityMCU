# DD-001 — RidingControl detailed design

RidingControl is the sole software component realizing the software-allocated system leaf LE-RIDING. It contains four separately specified units: U-SET-STATE, U-SESSION-ELIGIBILITY, U-SESSION-REPORT and U-DEMAND-ARBITER. Their stable identifiers and behavior are retained.

## Caller supplied execution time

Invocation timing follows the canonical caller supplied `ExecutionTime` contract in [Runtime Integration Contract](../../Runtime_Integration_Contract.md). Component-specific age, expiry and timeout ownership remains defined by each unit contract.


<a id="u-set-state"></a>

## U-SET-STATE — requested, pending and active settings

Consumes qualified current-context VD18MT requests, a concrete `AcceleratorPosition` on `acceleratorPositionIn`, and coherent qualified standstill evidence. It evaluates the contained `Qualification` and uses `Position` only when measurement validity, position qualification and freshness permit; the full record remains available when Position is unavailable. It retains distinct requested, pending and active state. On an interpretable speed request `r`, it applies the parent normalization `N(r)=r` for `0<r<40` km/h and `N(r)=40` for `r=0` or `r>=40`; unrecognized input changes neither valid active nor pending state. The latest valid pending settings apply atomically only when both guard facts hold. Active values remain otherwise, and active/pending speed never exceeds 40 km/h. After HMI loss, it may publish a current retained active-state snapshot with the original receipt provenance; HMI absence does not by itself age out a valid active selection or refresh the receipt. No received setting is inferred from initialization, retention, absence or an unqualified receipt.

<a id="u-session-eligibility"></a>

## U-SESSION-ELIGIBILITY — startup, authority and session inhibition

Eligibility starts ineligible in each new vehicle context. `U-SESSION-ELIGIBILITY` receives the concrete `AcceleratorPosition` once on `acceleratorPositionIn`, the exact software-refined `BrakeLeverState` once on `brakeLeverStateIn`, and the estimator's complete `MotorPositionRecord` once on `motorPositionIn`; it evaluates each contained qualification and retains diagnostic evidence even when semantic State or Position is unavailable. Motor-position Qualification preserves its source/reason/event-time/configuration/reset context and continues through this typed input without adding a new Ready guard or generic health route. Brake fault ordering uses Qualification's inherited source context and software recognition time/reason/configuration/reset context, never State measurement time. A recognized brake measurement fault reaches this unit in the full composite and latches current-session inhibition even if U-BRAKE-QUALIFY later requalifies live. Only the complete parent Ready guard issues an authority token with current context and expiry; any absent, invalid, expired or mismatched prerequisite withdraws it. A recognized parent-defined riding fault latches current-session inhibition, which cleared observation alone cannot remove. The unit consumes self-test results and does not claim their diagnostic coverage or physical inhibition. A qualified explicit Off request immediately closes the operation session, clears Ready eligibility and withdraws riding authority regardless of motion; unknown or unavailable is not Off. After On or controller wake, it starts fresh startup qualification and does not reuse prior authority, results or past-fault history. It grants a current expiring sleep request only while qualified Off and qualified traction `computeSleepPermitted` evidence remain true, revokes it when either condition ceases, and requires the existing traction output handoff before sleep eligibility is issued. Platform validates the current grant at actual entry and never renews it.

<a id="u-session-report"></a>

## U-SESSION-REPORT — selected fault reporting

It starts with qualified no-error in each context. With no selected fault, retain the earliest recognized reportable group fault; for an indistinguishable earliest set retain the lowest assigned code. `U-SESSION-REPORT` publishes that selected fault/no-error indication with its context and qualification to SC-HMI, which only encodes it. The selection persists until restart, above low-charge `0x01`; it cannot rank physical severity, clear inhibition or establish display receipt.

<a id="u-demand-arbiter"></a>

## U-DEMAND-ARBITER — signed torque arbitration

`U-DEMAND-ARBITER` is the one `SC-RIDING-CONTROL.V` policy decision point. It consumes separately typed snapshots, never a heterogeneous collection: `AcceleratorPosition`, the exact `BrakeLeverState` State/Qualification composite, `ActiveRidingSettings` (the dedicated active projection; pending settings are excluded), `RidingAuthority`, `BatteryOperatingLimitsAssessment` with its assessment timestamp, `QualifiedMotion`, `ActualTractionOutput`, current platform context/health, and its immutable compiled `DemandPolicyCalibration` parameters. It derives brake actuation only from qualified `Left`, `Right` or `Both` and evaluates State age locally from caller-supplied `ExecutionTime`. It emits `WheelTorqueRequest`; it neither activates settings, creates Session authority or a fault latch, evaluates battery protection, nor applies FOC/output control.

The command has `requestedWheelTorqueNewtonMetres: Real`, signed at the rear wheel: positive is forward propulsion and negative is regenerative braking. It also carries independent `maximumDischargeCurrentAmperes` and `maximumRegenerativeChargeCurrentAmperes`; these electrical allowances are forwarded to Traction for actual energy-transfer enforcement and do not determine wheel-torque sign. It carries `authorityGeneration`, `decisionSequence`, `decisionTimeMicroseconds`, `commandExpiryTimeMicroseconds`, producer/context and configuration identity, qualification and decision reason. Authority carries its own decision sequence/time and expiry. The command expiry is independently evaluated from authority expiry; matching authority generation is necessary but never extends either expiry. `U-TRACTION-ACCEPT` emits an accepted record with `effectiveAcceptedExpiryTimeMicroseconds=min(authorityExpiryTimeMicroseconds, commandExpiryTimeMicroseconds, acceptedAgeBound)` in the caller supplied monotonic domain; `U-TRACTION-CONTROL` rechecks that expiry using its `ExecutionTime`. A record is usable only when every required common contributing record is qualified, within its locally evaluated age bound, same current vehicle/reset generation, configuration-compatible and coherent at the declared decision snapshot. For `AcceleratorPosition`, measurement age is checked from `Position.sampleTimeMicroseconds`, while status and current source-health attribution come from `Qualification`. Any common producer, context, configuration/calibration or platform-health invalidation withdraws the prior command and diagnostic atomically; an unavailable electrical branch sets only its corresponding current allowance to zero and is not represented by its last value.

The arbitration is a bounded clamp, with separate non-negative propulsion and non-positive regeneration permissions. Pedal request maps through the active level profile to positive wheel torque. Level 0 allows no regeneration. Levels 1–5 use the parent provisional neutral at 35%; the compiled parameter set supplies their full and same-positive endpoints, ramps, taper and response parameters. Startup validation keeps the profile unavailable for missing, malformed or unvalidated required parameters. A lever blocks positive torque only; it may still permit accelerator-requested regeneration under the profile. The active speed limit and hard 40-km/h cutoff constrain both signs. `BatteryOperatingLimitsAssessment` carries independently qualified discharge and regenerative-charge amperes limits plus separate SOC positive-propulsion torque/speed caps. An unavailable electrical limit sets its allowance to zero; it does not directly select a wheel-torque sign. A low-SOC restriction constrains positive torque only. Demand forwards both electrical bounds with its wheel-torque request and never converts amperes to N m. Fault/authority withdrawal, missing common rider/motion/profile evidence, and every both-sign parent inhibition command zero. The approved 5-level exception omits comfort smoothing, but still applies the qualified low-speed taper. Demand does not manufacture a new rider choice, numerical threshold, ramp or taper.

Post-stop regeneration is a Demand-owned rearm state, initially disabled for each vehicle context and after qualified standstill. It remains disabled through hand-push movement. It re-arms only after the current `ActualTractionOutput` provides qualified evidence of forward travel together with qualified **positive applied wheel-torque** evidence in the same context/configuration; a commanded positive value, PWM state, Hall state/edge, speed alone, or a zero request cannot re-arm it. This rearm episode is separate from Demand's regenerative-restriction recovery episode: on each qualified partial or full restriction of rider-requested regeneration, RidingControl demand unit retains the reduced regenerative-charge permission/current allowance under that new internal episode generation. While the scooter remains moving and the accelerator remains continuously in the regenerative range, a later electrical-limit clearance or partial relaxation alone cannot increase the held allowance. Leaving the regenerative range or qualified standstill qualifies that episode before **or after** clearance; once both episode qualification and current qualified clearance/relaxation exist, Demand recovers automatically, including at standstill. BatteryProtection supplies current operating-limit assessments. U-DEMAND-ARBITER owns the regeneration recovery episode and post-stop rearm; RidingControl owns riding fault retention and restart.

For one decision snapshot, precedence is deterministic: (1) context/reset, platform-health, qualification/age/coherency failure in common rider/motion/profile evidence, expired or generation-mismatched authority, and both-sign parent inhibition withdraw both signs; (2) hard 40-km/h cutoff, active speed limit and qualified both-sign limits constrain both signs; (3) the post-stop/hand-push regeneration rearm gate and Demand-owned regeneration permission/recovery guards constrain **negative** torque only; (4) lever and SOC positive-torque/speed caps constrain **positive** torque only; (5) the active-level pedal/profile request and low-speed taper are clamped to the remaining sign-specific envelopes. An independently unavailable electrical allowance is zero and Traction enforces it in the actual current direction; it does not select a wheel-torque sign. If a simultaneous event withdraws a restriction while any tighter inhibition is present, the tighter inhibition wins; a recovery/increase never takes effect before the withdrawal/invalidation result in that snapshot. Equivalent sources must declare the same snapshot/coherency epoch; otherwise the decision is unavailable/zero, not ordered by transport arrival.

`DemandPolicyCalibration` is an owner-local immutable build parameter set, not an implicit constant or runtime dependency. It carries the level maps, full/end-point correspondence, neutral point, speed/taper shape, ramps, reference limits and symbolic response parameters used by the decision. A missing, malformed or unvalidated field makes the profile unavailable during startup/self-test. Its numerical values, bounds, units, owner, review state and verification are an end-to-end engineering gate: `SC-RIDING-CONTROL` releases each parameter with the matching input qualification and traction acceptance/physical-response verification. Changing it requires rebuilding, deploying and restarting the software. Until that happens, the design is **not implementation-ready** and must not claim a response time, ramp, taper, numerical speed threshold or physical torque tracking bound.
