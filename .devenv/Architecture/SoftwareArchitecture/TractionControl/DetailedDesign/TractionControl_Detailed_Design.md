# DD-001 — Software unit design: TractionControl

## Caller supplied execution time

Invocation timing follows the canonical caller supplied `ExecutionTime` contract in [Runtime Integration Contract](../../Runtime_Integration_Contract.md). Component-specific age, expiry and timeout ownership remains defined by each unit contract.


## Input, traction and platform derivation gates

`U-TRACTION-MOTION` is the sole detailed producer of `QualifiedMotion` for Demand, Settings and Session: it publishes vehicle speed, travel direction and standstill independently of Ready and command acceptance only by interpreting current Hall capture/position evidence with capture health, owner-local compiled map/pole-pair/final-drive/loaded-wheel parameters and a released bounded-observability/standstill criterion. These calibration, capture-health and timing/uncertainty criteria are named engineering gates; until they are accepted, it publishes Unknown/unavailable. A static Hall state, an absent edge alone, command or output-enable state is not vehicle motion. `U-TRACTION-ACTUAL-OUTPUT` produces `ActualTractionOutput` as a qualified applied-wheel-torque **estimate** from current post-stage physical facts with source/timestamp provenance plus same-operation phase-current/position and qualified vehicle-motion evidence, using its immutable compiled `ActualOutputEstimationCalibration`; it runs during startup, disarmed and withdrawn states as an observation function. `U-TRACTION-ACCEPT` evaluates authority/command acceptance separately and cannot gate, refresh or manufacture that observation. `actualAppliedWheelTorqueNewtonMetres`, active electrical braking and powered-forward-travel are unavailable if any estimator evidence, parameter check or generation match is absent; a requested command, FOC reference, acceptance result, CCR/PWM state or output-stage event alone is insufficient. These observations are never proof of physical torque, braking or energy direction. `U-TRACTION-CONTROL` consumes only a current accepted signed demand, independently rechecks its effective expiry/context, and uses the selected FOC realization to form `PWMAndADCSamplingPlan` including the next `CCR1..3`, `CCR4` sampling plan and ADC context. `U-TRACTION-OUTPUT` alone performs the guarded literal register stage/commit, consumes independently observed stage/protection evidence, and publishes the typed phase-excitation command; its output observation stays on the internal actual-output-estimation route.

`U-TRACTION-CONTROL` and `U-TRACTION-OUTPUT` implement the completed fast-epoch, command-data and literal latch sequence defined by the [allocated traction HSI](../../../DRV8300DRGE-EVM/DRV8300DRGE-EVM_WeAct_STM32H723VGT6_Traction_HSI.md) and [runtime integration contract](../../Runtime_Integration_Contract.md). The latter distinguishes project bindings from generic drivers and direct fast calls from scheduled routes. Their distinct ASW requirements and Unit children are recorded in the Control Unit Requirements catalogue. Electrical/sensing, command representation, response bounds, host resources, reset domains, retention integrity, physical outputs and diagnostic coverage remain parent acceptance gates.

## Draft MotorControl specialization pilot

This draft controlled pilot follows one architecture chain only: the system logical leaf `LE-MOTOR-CTRL` is modeled by `MotorControl`, `MotorControlRealization` specializes that boundary, contains the sole SC control core and references the separate acquisition, temperature and supply components, and `TractionControlImplementation` remains the selected detailed implementation of that core. The wrapper allocates physical temperature/supply measurement responsibilities to the existing acquisition/conversion chains; it creates neither an identity flow from physical values to ADC records nor a second sensor input. The implementation owns the five existing traction units shown below; those units remain unit parts and are not new component types, runtime components or tasks.

The logical wrapper and software views select one detailed core implementation occurrence. SysML `:>>` feature redefinitions carry that selection through the chain; they do not create a second MotorControl or TractionControl instance. The wrapper's existing sensor-component references establish the expanded logical responsibility without claiming that the core performs raw sensor conversion. The selected containing context is defined by the detailed-design model. See the [system MotorControl model](../../../SystemArchitecture/Modelling/TractionControl/Decomposition/MotorControl.sysml), [software TractionControl model](../TractionControl.sysml), the [TractionControlImplementation model](TractionControlImplementation.sysml), and [detailed-design container model](../../DetailedDesign/Modelling/X2CityDetailedDesign.sysml).

The selected logical container path is `vehicle.epcs.traction.tractionControl.motorControl`. The detailed model specializes `TractionControl` and redefines its `motorControl` to the realization wrapper, then specializes `Traction` as `SelectedTraction`, `ElectricalPropulsionControlSystem` as `SelectedEpcs`, and `ProjectVehicleModel` as `VehicleDetailedDesign`. The existing `vehicle.traction` path is retained as a reference alias to the selected sole core occurrence. The system `x2CityVehicle`, software `tractionControlVehicle`, and `motorControlRealizationVehicle` views are bound inside the detailed-design model to the same realization chain.

The selected chain preserves the existing allocation and requirement IDs. It does not imply that the other system/software/detailed-design chains have been migrated to the same specialization pattern.

### TractionControl boundary to unit ownership

The table maps every public TractionControl boundary port to the existing detailed unit owner. `P-*`, `SW-I-*` and `R-*` references remain the canonical ARCH-003 contracts; unit model files are linked for review of the corresponding ports.

`U-TRACTION-ACCEPT` forwards the independently produced actual-output record to Demand without gating or refreshing it. It also evaluates qualified temperature, fast PVDD, regular GVDD, conversion health, and independently observed stage/protection evidence into current categorized condition evidence for Session, independently of authority acceptance. Session alone owns recognized-fault latching, report selection and restart lifetime. `U-TRACTION-MOTION` keeps its Hall capture/position-specific health qualification, while `U-TRACTION-CONTROL.sensorHealthIn` remains the broader FOC health fan-in. `U-TRACTION-CONTROL` produces the sampling plan, while `U-TRACTION-OUTPUT` remains the sole literal stage/commit owner and publishes the typed phase-excitation command with overriding inhibition. This mapping records ownership and traceability; it does not change any requirement body or select a new execution mechanism.

External detailed-design traffic for this pilot terminates at the public `TractionControlImplementation` boundary. The implementation model contains the five unit-to-unit flows once; the `vehicle.traction` reference alias does not add a second wiring graph.

The pilot retains the shared qualification context ancestry: software `ContextualSoftwareInformation` refines the logical qualified-information record, and detailed `UnitInformationEnvelope` refines that software context. Traction receives one estimator-owned `MotorPositionRecord` at its public boundary and forwards that same complete record to control, motion and actual-output units; its `SoftwareMotorPositionQualification` preserves source/reason/event-time/configuration/reset context for local gating even when Position is unavailable. `HallObservationRecord` remains the Hall contribution, while `PhaseCurrentFeedbackRecord` and `FastDcLinkVoltageRecord` retain their existing direct feedback roles. The DD observation boundary `TractionObservationRecord` refines `TractionObservation` while retaining `UnitInformationEnvelope`. Software `ExpiryTimeMicroseconds` is an `Integer` refinement, while logical `Expiry` remains abstract and opaque. Values, field meanings and expiry semantics remain unchanged; this schema alignment is scoped to the MotorControl pilot and does not alter requirement contracts.
