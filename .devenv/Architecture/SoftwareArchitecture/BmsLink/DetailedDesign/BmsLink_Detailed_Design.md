# DD-002 — Battery protection and BMS software-unit design: BmsLink

## Caller supplied execution time

Invocation timing follows the canonical caller supplied `ExecutionTime` contract in [Runtime Integration Contract](../../Runtime_Integration_Contract.md). Component-specific age, expiry and timeout ownership remains defined by each unit contract.


## SC-BMS-LINK

### Units, interfaces and executable order

`U-BMS-LINK-TRANSACTION` accepts only read transactions for `0x03`, `0x04`, and `0x05`, and its existing output remains the gate to the decoder. It first checks generic frame integrity independently of payload content: complete and unambiguous boundaries, declared/received length consistency within protocol bounds, and checksum. It then applies transaction acceptance: the response must match the current request/command and report success. Only a frame-valid, transaction-accepted response is forwarded. A valid error-status response, including a valid zero-payload response, is frame-valid but has no measurement outcome; a frame-valid wrong-command response is not accepted as solicited data. Neither case is a malformed-frame finding. Per-command counts, encodings and exact schema shape are decoder responsibilities, not generic frame-integrity checks.

The selected implementation is fixed to the SP14S004 V1.0 read protocol with owner-reported firmware 3.2. Firmware 3.2 is device identity, not a protocol version. There is no runtime layout inference or general extension support requirement. On every normal or unexpected vehicle-controller startup, exactly two dedicated startup checks must both pass from the current startup's accepted `0x03` reply before dependent outputs qualify: firmware version 3.2 and reported series-group count 14. Firmware is decoded with the evidence-qualified installed-unit encoding; no raw byte, offset, or payload length is assumed. Missing, invalid, or mismatching either value leaves dependent BmsLink observations unqualified; BatteryProtection then publishes zero effective current for unqualified dependent limits. Startup qualification is internal and creates no public flag or port. Runtime `0x05` identity remains informational only and never blocks or orders startup. Hardware V1.0, model, and configuration acceptance remain commissioning evidence.

`U-BMS-LINK-DECODE` dispatches accepted payloads by command and checks every accepted response against its implemented fixed schema, including the first startup `0x03` reply: command-specific payload length, field count and encoding must all match before any dependent value qualifies. These checks are distinct from generic frame integrity: a frame can pass the latter yet fail its command schema, such as a `0x04` group payload containing 13 values where exactly 14 are required. `0x03` current/capacity scale remains bound to the same response; only a scale supported by the selected profile is applied; signed-current meaning is preserved; reported series count 14 is required before dependent pack data qualifies. Preserve the separate qualified protection-path states from the selected `0x03` source representation: bit 0 is charge-path enabled and bit 1 is discharge-path enabled, with 1 meaning enabled. Do not collapse the two states or infer capability magnitude or physical path protection. `0x04` requires exactly 28 bytes of 14 ordered big-endian mV group values and preserves position identity. `0x05` uses only the implemented fixed encoding and payload shape. Decoded temperature-reading count must equal the accepted Basic response's declared NTC count, and probe identifiers must be unique and match selected profile channel assignments; conversion preserves probe position and uses the approved conversion. A field semantic failure withholds only the affected observation; a transaction/schema-rejected response supplies no new qualifying evidence. These schema checks are software guards, not a claim that payload mappings or accepted lengths have been verified by engineering evidence. Raw mappings, actual payloads and accepted lengths remain open evidence. The decoder does not infer source accuracy, actual SOC, physical plausibility limits, or configuration identity from generic protocol material.

`U-BMS-LINK-PUBLISH` updates a field only from the decoder's accepted, internally consistent result. Private per-source/per-field elapsed timers use caller-supplied `ExecutionTime` from the last accepted matching response; they are not part of `BatteryMeasurements`. They bound host time since that response and are evaluated with conservative remote-update-latency/source-validity uncertainty, not as a BMS sample timestamp or proof of the BMS sampling interval. Only a newly accepted response that contains the matching field resets that field's timer, even when the value is unchanged. Here accepted means both frame-valid and accepted for the current request, then successfully decoded for that field. An unrelated command, frame-valid wrong-command or error-status response, malformed frame, schema-invalid response, cached republication, or transaction reply timeout resets no source timer. A valid error response has no measurements to decode. Normal BmsLink invocations check these bounds even when no decoder frame was accepted; expiry withdraws the affected field qualification and publishes the resulting current status. A malformed/inconsistent frame supplies no qualifying update; an optional-field failure need not invalidate independently accepted fields. At every vehicle-controller startup, publish the existing `BatteryMeasurements.sourceContext` for the current producer boot and begin affected fields, including optional nominal capacity, unavailable. Ordinary field timeout withdraws only that field qualification and retains the field value and source context. Producer timer state begins unqualified; old trust is not restored across controller startup. A wake or short interruption alone retains an otherwise justified unexpired field. It emits each field and set with value, qualification, fixed-schema scale, probe/group metadata and BMS producer context, without source-age timestamps.

Execution is: request/receive → transaction gate → command decoder → field/set qualification → atomic publication. Accepted frames update only the fields they contain; a regular invocation also publishes qualification transitions on expiry even when no new frame arrived. Consumers may combine fields only through their own cross-field qualification. A transaction reply timeout is transport status only: it does not itself expire otherwise unexpired source data. Periodic qualification snapshots may monitor liveness, but never refresh source-newness timers. Command order, retry policy, polling rate, response deadline and numeric source-age/update-latency bounds remain engineering gates derived from captured selected-unit behavior and energy/control budgets; no remote BMS sample time or update latency is inferred from a host reply.

### State, reset and invariants

Volatile state is the outstanding read command, accepted field/set records, receipt timestamps and current BMS source context. Vehicle-controller startup establishes the current producer boot context. Ordinary field expiry withdraws only the affected qualification and retains the value and context. None of this state is restored across host reset. `0x04` failure cannot corrupt prior independent `0x03`/`0x05` records, although consumers must withhold a permission that needs the complete group set.

Invariants: no rejected frame changes an observation; a group set is qualified only with 14 values; a current/capacity value always carries its response's scale; an accepted identity remains an observed identity, not immutable pack proof; and no interface exposes BMS write/control capability.

### Acceptance scenarios

Software vectors cover captured fixed-profile `0x03/04/05`, generic frame-integrity failures (boundary, declared/received length consistency, protocol bounds, checksum), transaction-acceptance outcomes (status and wrong command), command-schema length/field-count/encoding faults, concatenated/truncated frames, both implemented scale modes and signed-current boundaries, 13/14/15 group counts, and optional-temperature loss. A frame-valid wrong-command or error-status response refreshes no source timer; a frame-valid but schema-invalid response such as a 13-value group payload is rejected by the decoder. Integration scenarios cover the two startup values together in the current accepted `0x03` reply, either missing/invalid/mismatching, dependent observations held unqualified and BatteryProtection effective currents zero, and sleep/wake, host reset, delayed/missing responses and recovery. Runtime `0x05` identity must not block or order startup. Electrical coupling, installed-unit encoding, hardware/model/configuration acceptance, actual payload/schema mapping, measurement comparison and timing/power qualification remain commissioning or engineering evidence, not acceptance claimed by this design.
