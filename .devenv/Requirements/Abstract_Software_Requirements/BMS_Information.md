## Selected-unit UART read acceptance contract

This contract defines acceptance for read-only use of `0x03`, `0x04` and `0x05`. Its protocol facts are from the manufacturer V12 source recorded in [BAT-001](../../Battery/BAT-001_Selected_Pack_and_BMS.md#fixed-inputs-and-provenance); selected-board firmware/configuration support remains evidence to capture, not an assumption from the generic protocol.

| Acceptance subject | Contract and evidence / distinguishing verification |
|---|---|
| Transaction envelope | A request is `DD A5 command length payload checksum 77`; its response is `DD command status length payload checksum 77`. For every accepted response, prove start/end bytes, echoed requested command, success status, declared length exactly matching received payload, and the V12 16-bit two's-complement checksum over response status/length/payload. Reject truncation, surplus/concatenated data not unambiguously framed, bad checksum, non-success status and another command as a whole-response failure; none may refresh any field. Capture byte-exact selected-unit exchanges for each supported command. |
| `0x03` basic information | Establish the selected firmware's supported base-layout length and offsets from a captured response and the manufacturer source before allocating fields. Qualify pack voltage at 10 mV, signed two's-complement current (positive charging; negative discharging), remaining/nominal capacity and RSOC, reported version, protection/balance/path state, series count and available temperatures only when their enclosing response and applicable fields are present and internally consistent. The FET-status scale bit selects 10 mA/10 mAh or 100 mA/100 mAh; decode current and capacity with the scale from that same response. Require reported series count `14` for pack-data qualification. Do not assign accuracy to current, RSOC or capacity, or treat RSOC as actual SOC, until separately qualified. |
| `0x04` group voltages | Accept only an even payload containing exactly 14 high-byte-first group values (28 bytes), in fixed reported group order, each in mV. Associate group identity with its response position; a count mismatch, missing group or implausible/contradictory group set invalidates the `0x04` group-data set. It does not corrupt an independently accepted `0x03` or `0x05` value; dependent system permission still becomes unavailable if the complete required group set or cross-field qualification is lost. Qualify physical range, inter-group consistency and any comparison to pack voltage against independently derived measurement uncertainty; no numeric plausibility bound is selected here. |
| `0x05` identity | Accept the device/version identification string only after envelope validation and selected-unit-supported length/encoding qualification. Record it with the `0x03` reported version and actual board/firmware/configuration identity for integration acceptance. A generic V12 extension, optional field or an unrecognized string is not decoded or used as configuration proof. |
| Temperature, signs and units | Convert each available temperature as `(raw - 2731) / 10` °C and retain probe position/count. A missing optional temperature affects that probe only after the selected layout establishes its absence; an invalid conversion, count/layout conflict or unavailable required field makes that field unknown. Never substitute ambient, previous, zero or display values for qualified battery temperature. |
| Validity, freshness and recovery | Store raw receipt time separately from measurement age: a valid response refreshes receipt freshness only and supplies no measurement timestamp/age unless the selected unit proves one. After host startup, recognized BMS reset or loss of required source qualification, newly accepted observations must requalify the affected information before use. A wake or short communication interruption alone does not invalidate otherwise justified unexpired observations. Individual fields may degrade independently for a valid response with an absent/invalid optional field; a malformed envelope or inconsistent layout supplies no qualifying update for any field from that frame. Previously accepted values may remain usable only within their independently justified age and consistency bounds; a separately recognized fault still acts immediately under its assigned response. Consumers shall see qualified, unknown, invalid and stale states distinctly. Requalification does not clear an existing system fault latch. Commissioning/identity checks need not share the periodic freshness deadline of dynamic safety-related values; justify each consumer dependency. |
| Timing and power trade-off | Derive command order, poll interval, response deadline, retry count, stale threshold, startup qualification deadline and any wake/recovery sequence from captured selected-unit response behavior, dependent-control reaction budgets and the BMS running/sleep/shutdown energy budget in BAT-001. Demonstrate that polling meets active-control information needs and fitted/detached storage budgets; permitted active operation need not preserve sleep. No fixed polling, timeout or sleep number is set by this requirement. |
| Acceptance test classes | `T-SW`: recorded valid `0x03/04/05` vectors; checksum/framing/status/wrong-command/length corruption; signed-current and both scale-mode boundaries; 14/13/15 group counts; temperature conversion; optional-field loss; concatenation and interruption. `T-SYS`: selected-unit startup, sleep/wake, BMS/host restart, delayed/missing replies and recovery; compare voltage, current direction, group order and available temperatures with suitable independent references; show stale/unknown data and display fallbacks cannot authorize dependent operation. |

Open qualification inputs are the installed board/firmware/configuration identity; supported `0x03` and `0x05` layouts/lengths and encodings; actual probe count; electrical-interface arrangement; response and wake behavior; physical measurement accuracy, latency and uncertainty; and derived plausibility, freshness and polling limits. These are acceptance evidence and parameter derivations under `OI-041/061`, not generic-protocol defaults or new requirements.
