| <a id="req-sys-spd-008"></a>`REQ-SYS-SPD-008` | After valid speed-setting receipt, unrecognized speed values shall preserve the existing valid active/pending setting state and its application guards. | `I`, `T-SYS`, `T-FI`. Test unrecognized requests with a distinct active/pending pair, both moving and at the guard. An interpretable zero or above-40 request instead becomes 40 and replaces the pending request. | [DEC-SPD-001](../DEC-001_Decisions_and_Open_Issues.md#dec-spd-001), [DEC-FLT-001](../DEC-001_Decisions_and_Open_Issues.md#dec-flt-001) | `WS-OI-007`, `WS-OI-008`, `WS-OI-009`, `WS-OI-010`, `WS-OI-015`: Decoded zero means no limit requested and normalizes to 40 km/h; other special encodings and whole-frame handling remain open. |

For an interpretable request r in km/h, normalization is N(r)=r when 0<r<40, otherwise N(r)=40 for r=0 or r≥40. This defines no interpretation for missing, invalid or other special encodings. Qualification/decoding precedes normalization; no received value means no startup speed-setting qualification.

Process accepted requests in their established order, retain the latest valid normalized request, and evaluate the standstill/physical-rest application guard against coherent current observations. At a qualifying application decision, use that latest request without replaying obsolete ones. An unrecognized request neither overwrites nor cancels existing valid active/pending state, including while the guard is true. A pending setting never changes the active cutoff; cutoff/recovery at the active value and the unconditional 40 km/h ceiling do not wait for this guard. Qualification, transport order, numeric limits and finite application timing remain IF-A-001/002 and WS-OI-001/002/008/009/015 work; no new frame format, simultaneous-frame priority or host is selected.

### REQ-SYS-CTL-002 detailed-design trace and release gate

The approved `REQ-SYS-CTL-002` body above is unchanged. Its `U-DEMAND-ARBITER` realization is [UR-DEMAND-001](../Unit_Requirements/Control_Unit_Requirements.md#ur-demand-001) and [DemandPolicy detailed design](../../Architecture/SoftwareArchitecture/DemandPolicy/DetailedDesign/DemandPolicy_Detailed_Design.md#u-demand-arbiter). Those children make the command record, typed evidence, invalidation, sign-specific permissions, post-stop rearm evidence and simultaneous-event precedence inspectable; they do not add a rider decision or replace any parent-system physical-output verification.

The following derived values remain an engineering release gate, with the named calibration/contract owner and the listed end-to-end verification required before implementation acceptance: the full level maps and same-positive endpoints, 35% neutral interpretation, ramps and low-speed taper shapes, velocity/standstill interpretation, freshness/coherency and authority/command expiry bounds, and command-transfer/traction-response bounds. SC-DEMAND owns immutable compiled `DemandPolicyCalibration` parameters containing the maps, endpoint/reference limits and symbolic timing parameters. Startup validation against firmware build identity/static initialization, including the build-validation flags, is required before use; it supplies no implicit numeric default. A missing, unreleased or failed-validation value must yield unavailable/withdrawal behavior under the detailed contract; an unavailable per-sign battery branch withdraws only that branch and never enlarges it. Changing these parameters requires rebuilding, deploying and restarting software, and does not create an activation or runtime-context transition. This is not evidence that the policy is implementation-ready.
