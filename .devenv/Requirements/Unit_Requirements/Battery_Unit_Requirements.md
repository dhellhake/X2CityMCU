# Battery unit requirements

**Draft caller-time successor — 2026-09-17; retains REQ-001-R1.9.** These are detailed-design Unit Requirements. Each has one unit target and derives only from its named approved Abstract Software Requirement. System/HW constraints cited by the parent remain sources/dependencies, not parents. The units and supporting design are in [DD-002](../../Architecture/SoftwareArchitecture/DetailedDesign/DD-002_Battery_Protection_Unit_Design.md).

`U-BMS-LINK-TRANSACTION`, `U-BMS-LINK-DECODE`, `U-BMS-LINK-PUBLISH`, `U-BAT-POLICY-EVALUATE`, `U-BAT-POLICY-RESTRICTION`, `U-SERVICE-INFO-COLLECT` and `U-SERVICE-INFO-SNAPSHOT` receive `executionTimeIn` from their immediate caller. A dispatched component or standalone unit receives a live host-boot monotonic `currentTimeMicroseconds` sample immediately before invocation; nested units inherit that bounded invocation's fixed reference and do not read a clock or resample it. The reference is not reused for another invocation. They use it for any private response, measurement-age, expiry or timeout rule, conservatively including maximum remaining bounded execution to the relevant use/effect. BMS packet receipt time remains distinct from actual BMS measurement age, and a newly accepted valid acquisition refreshes only the affected measurement timer even when its value is unchanged. BMS reset/requalification and riding first-fault/session latching retain their existing independent behavior. Verify live pre-invocation caller sampling, fixed nested forwarding, reset generation, queued old replies, same-value reacquisition, health-only/composite republication and each affected timeout under `REQ-SYS-PLT-002`; no supplied BMS firmware obligation is created.

## Unit Requirements

| ID | Requirement | Parent Abstract Software Requirement | Target | Planned verification |
|---|---|---|---|---|
| <a id="ur-bms-link-001"></a>`UR-BMS-LINK-001` | The transaction unit shall publish no qualifying BMS update from a response unless the response is unambiguously framed and passes start/end, requested-command echo, success-status, declared-length and checksum validation. | `REQ-SYS-BMSIF-001` | `U-BMS-LINK-TRANSACTION` | `T-SW`: valid and independently corrupted transaction vectors. |
| <a id="ur-bms-link-002"></a>`UR-BMS-LINK-002` | The decode unit shall represent accepted `0x03`, `0x04` and `0x05` data with the response-specific scale, sign, group/probe identity and qualification needed by consumers, and shall make unsupported/invalid fields unavailable without inventing a value. | `REQ-SYS-BMSIF-001` | `U-BMS-LINK-DECODE` | `T-SW`: scale/sign, 14-group, temperature and optional-field vectors. |
| <a id="ur-bms-link-003"></a>`UR-BMS-LINK-003` | The publication unit shall distinguish receipt freshness from measurement age and shall require affected information to requalify after host startup, recognized BMS reset or loss of required source qualification. | `REQ-SYS-BMSIF-001` | `U-BMS-LINK-PUBLISH` | `T-SW`: context/reset/staleness transitions; `T-SYS`: selected-unit recovery. |
| <a id="ur-bat-policy-001"></a>`UR-BAT-POLICY-001` | The evaluation unit shall issue separate qualified charge and discharge envelope candidates with operation-specific restriction reasons or recognized battery-fault information, and shall withhold a dependent permission when a required input is unavailable. | `REQ-SYS-BMSPOL-001` | `U-BAT-POLICY-EVALUATE` | `T-SW`: varied input availability and overlapping restriction/fault cases. |
| <a id="ur-bat-policy-002"></a>`UR-BAT-POLICY-002` | The restriction unit in the vehicle instance shall retain the reached-10%-cutoff positive-propulsion restriction as qualified operating state until qualified actual SOC exceeds 20%, without representing that state as fault history. | `REQ-SYS-BMSPOL-001` | `U-BAT-POLICY-RESTRICTION` | `T-SW`: entry/recovery/reset-candidate cases; `T-SYS`: retention integration. |
| <a id="ur-service-info-001"></a>`UR-SERVICE-INFO-001` | The collection unit shall invalidate an affected cached source observation on that producer's context change and preserve the producer, context, validity, freshness and qualification of each current observation. | `REQ-SYS-SVCIF-001` | `U-SERVICE-INFO-COLLECT` | `T-SW`: producer restart, stale/unavailable and BMS-only reset cases. |
| <a id="ur-service-info-002"></a>`UR-SERVICE-INFO-002` | The snapshot unit shall expose current available and unavailable service information while distinguishing check result, current fault, retained inhibition/restriction, selected indication, requested output and qualified actual output, without a control path that changes operation. | `REQ-SYS-SVCIF-001` | `U-SERVICE-INFO-SNAPSHOT` | `T-SW`: mixed-source snapshots; `T-SYS`: compare with independent physical evidence. |

The requirements do not allocate BMS writes, vendor internals, physical energy paths, host/electrical realization or numeric thresholds. Their parent Abstract Software Requirements are in [BMS Information](../Abstract_Software_Requirements/BMS_Information.md), [Battery Capability Policy](../Abstract_Software_Requirements/Battery_Capability_Policy.md), and [Service Information](../Abstract_Software_Requirements/Service_Information.md).
